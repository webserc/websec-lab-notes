# 第一部分：0 和 1 是怎么变成文件的

## 1.1 一切从 bit 开始

**bit（位）** = 一个 0 或一个 1。计算机里最小单位。

**byte（字节）** = 8 个 bit。

```
8 bit  = 1 byte  = 256 种可能（2⁸）
```

一个字节能表示的数值范围是 **0 到 255**。

## 1.2 为什么用十六进制

写 `10101010` 太长了，人看不下去。

**十六进制**是 4 个 bit 一组，一个字符表示 0-15：

| 十进制 | 二进制 | 十六进制 |
|---|---|---|
| 0 | 0000 | 0 |
| 9 | 1001 | 9 |
| 10 | 1010 | A |
| 15 | 1111 | F |
| 255 | 11111111 | FF |

**所以一个字节 = 2 个十六进制字符。**

```
10101010  →  AA
11111111  →  FF
00000000  →  00
```

## 1.3 `0x` 是什么

`0x` 只是一个前缀，意思是"后面这个数是十六进制的"。

```
0xFF   = 十进制 255
0x41   = 十进制 65
0x89   = 十进制 137
```

看到 `0xFF`，别被吓到，它就是"十六进制的 FF"，也就是"这一个字节的值是 255"。

## 1.4 手算一遍：`GIF89a` 为什么是 `47 49 46 38 39 61`

`GIF89a` 是 6 个字符。每个字符在 ASCII 表里都有一个编号。

ASCII（美国信息交换标准代码）就是一张"字符 → 编号"的对照表。

| 字符 | ASCII 十进制 | 十六进制 |
|---|---|---|
| G | 71 | 47 |
| I | 73 | 49 |
| F | 70 | 46 |
| 8 | 56 | 38 |
| 9 | 57 | 39 |
| a | 97 | 61 |

连起来：`47 49 46 38 39 61`

**这就是为什么你 `xxd` 看到 `GIF89a` 那行显示的是 `4749 4638 3961`。**

**不是魔法，就是 ASCII 编号。**

## 1.5 反过来：不可打印的字节

有些字节值在 ASCII 表里没有对应字符（比如 1-31 是控制字符）。

| 值 | 十六进制 | 显示成什么 |
|---|---|---|
| 255 | FF | 不可打印 |
| 216 | D8 | 不可打印 |
| 137 | 89 | 不可打印 |

**所以 JPEG 的开头 `FF D8 FF` 在记事本里打不开、看不见——它是"不可打印字节"，只能显示成乱码或者干脆不显示。**

**这就是为什么"文件头"必须用十六进制编辑器（xxd、WinHex）看，不能用记事本。**

# 第二部分：文件类型是"认"出来的

## 2.1 没有"文件类型"这种东西

硬盘上只有一堆字节。**"这是图片""这是代码"是软件自己判断出来的。**

判断方式有三种，可信度从低到高：

**第一，看扩展名。** `.jpg` 就认为是图片。

**最不可靠**——扩展名是文件名的一部分，随便改。你传 `shell.php` 改成 `shell.jpg`，它还是 php 代码。

**第二，看 `Content-Type`。** 上传时浏览器会带一个类型标签。

**也不可靠**——这个字段是客户端写的，curl 一句 `;type=image/jpeg` 就能伪造。

**第三，看文件开头的字节。** 每个格式有自己的固定开头。

**这个最可靠**——因为改它就得改文件内容本身。

## 2.2 魔数（magic number）

**一句话：每种文件格式约定了一组固定的起始字节，用来标识自己。**

| 格式 | 起始字节（十六进制） | 显示成字符 |
|---|---|---|
| GIF | `47 49 46 38` | `GIF8` |
| JPEG | `FF D8 FF` | 不可打印 |
| PNG | `89 50 4E 47` | `\x89PNG` |
| ZIP | `50 4B 03 04` | `PK` |
| PDF | `25 50 44 46` | `%PDF` |

## 2.3 为什么是"开头"几个字节

**因为读取器只需要判断"我认不认识这个开头"，不需要读完整个文件。**

一个 100MB 的视频，判类型只读前 4 个字节。**这是性能优化，也是漏洞来源。**

## 2.4 PNG 那个奇怪的 `0D 0A 1A 0A`

PNG 的开头是：

```
89 50 4E 47 0D 0A 1A 0A
```

前四个 `89 50 4E 47` 就是 `\x89` + `PNG`。

**后面那四个 `0D 0A 1A 0A` 是历史遗留的防御：**

| 字节 | 十六进制 | 含义 |
|---|---|---|
| `0D 0A` | CR LF | Windows 换行 |
| `1A` | EOF | 文件结束符（DOS 时代） |
| `0A` | LF | Unix 换行 |

**原因：** 早年文件要通过调制解调器、邮件系统传输，那些系统会"自动修正换行符"，把 `0D 0A` 改成 `0A`，把文件内容搞坏。

**PNG 的作者故意在开头放这几个字节，这样如果中途被改了，校验就会失败，立刻发现文件损坏。**

而 `1A` 是 DOS 的"文件结束"标记，放进去能让老式 DOS 工具读到这就停，不再往下读——防止它在二进制文件里乱解析。

**这段是设计智慧，也是你在 `xxd` 里看到 PNG 开头后面跟着莫名其妙几个字节的原因。**

# 第三部分：三种图片格式的内部结构

> 只需要懂"哪里能塞东西"，不用背全部格式。

## 3.1 JPEG

**结构是"标记段"拼接。** 每个段以 `FF` 开头 + 一个标识字节。

```
FF D8                     ← SOI（Start Of Image）文件开始
FF E0 00 10 "JFIF" ...    ← APP0 段，存"这是 JFIF 标准"
FF DB ...                 ← DQT 段，量化表
FF C0 00 11 08 02 58 03 20 ← SOF0 段，里面存高度和宽度
FF DA ...                 ← SOS 段，真正的图像数据从这里开始
...（压缩后的像素数据）...
FF D9                     ← EOI（End Of Image）文件结束
```

**关键几点：**

`FF D8` 是开头。**任何 JPEG 都以这两个字节开头。**

`FF C0` 段的第 5-8 字节是**高度和宽度**。`getimagesize` 就是从这里读尺寸的。

`FF D9` 是结尾。

**`FF D9` 之后还能有东西吗？**

**能。** 大多数解析器读到 `FF D9` 就认为"图片结束了"，后面的字节**直接忽略**。

**这就是图片马的入口：把 php 代码放在 `FF D9` 之后。**

## 3.2 PNG

**结构是"数据块（chunk）"串联。**

```
89 50 4E 47 0D 0A 1A 0A   ← 文件签名（8 字节）
```

之后是若干个 chunk，每个 chunk 结构固定：

```
[长度 4 字节][类型 4 字节][数据 N 字节][CRC 4 字节]
```

| chunk 类型 | 干什么 |
|---|---|
| `IHDR` | 必须是第一个，存宽、高、色深 |
| `PLTE` | 调色板（索引色时才有） |
| `IDAT` | 真正的像素数据，可以有多个 |
| `tEXt` | 存文本（作者、软件名等） |
| `IEND` | 最后一个，表示结束 |

**`tEXt` 这个 chunk 就是图片马的藏身处。**

因为它本来就是"存文字"的，里面塞什么都合规。

**而且二次渲染（重新编码）时，很多实现会保留 `tEXt` 元数据**——这就是绕过二次渲染的一个方向。

## 3.3 GIF

```
"GIF89a"        ← 头（6 字节）
[逻辑屏幕描述符]  ← 宽高、色深等 7 字节
[全局调色板]     ← 颜色表
[若干数据块]
  0x21 ...      ← 扩展块（注释就在这）
  0x2C ...      ← 图像描述符 + 图像数据
0x3B            ← 结尾
```

**`0x21 0xFE` 是"注释扩展块"**，里面可以放任意文本。

**`0x21 0xFF` 是"应用扩展块"**，也常被用来藏东西。

**GIF 的 89a 比 87a 多了这几个扩展块**——所以老 GIF 塞不进注释。

# 第四部分：解析器为什么"偷懒"

## 4.1 getimagesize 干了什么

PHP 的 `getimagesize("file")` 返回一个数组：

```php
[
  0 => 宽,
  1 => 高,
  2 => 格式编号（1=GIF, 2=JPEG, 3=PNG, ...）,
  3 => "width=xxx height=yyy",
  ...
]
```

**它内部做的事：**

**步骤一，读文件前几个字节，判断格式。**

```
FF D8  → JPEG
89 50 → PNG
47 49 → GIF
```

**步骤二，按格式跳到对应位置，读宽高。**

JPEG 就往后找 `FF C0`，读那 4 个字节。

PNG 就读 `IHDR` chunk 的内容。

GIF 读逻辑屏幕描述符里的 7 个字节。

**步骤三，返回数组。**

**它不读像素，不解码图像，不验证完整性。**

## 4.2 这就叫"解析器只读它需要的那部分"

**一个 10MB 的图片，getimagesize 只读前几百个字节。**

所以：

```
[真的 JPEG 头 + 几百字节][一堆合法的图片数据][<?php system($_GET['c']); ?>]
                        ↑
                    getimagesize 读到这就够了
                    ↑                          ↑
              它认为"这是个合法 JPEG"        这一段它没看
```

**这就是图片马的完整解释。**

**不是"文件头伪装"这么模糊的说法，而是：解析器只检查到某一点就停，后面的部分对它来说是"垃圾数据"。**

## 4.3 但"能上传"不等于"能执行"

这里是关键。

`shell.jpg` 传上去了，`getimagesize` 通过了。

**但是** 访问 `shell.jpg` 的时候，Apache 按 `FilesMatch` 判断，`.jpg` 不匹配 PHP 处理器，**于是它把整个文件原样发给你**——包括你那段 php 代码。

**你看到的是源码，不是执行结果。**

**所以图片马必须配合第二个漏洞才能生效：文件包含。**

# 第五部分：文件包含——让 `.jpg` 被执行

## 5.1 include 干了什么

PHP 里的 `include` / `require`：

```php
include($_GET['page']);
```

**它做的事：把指定路径的文件内容读进来，当成 PHP 代码解析执行。**

**注意：它不看扩展名。**

`include("shell.jpg")` 会把 `shell.jpg` 的内容读进来，**只要有 `<?php ... ?>` 标签，里面的代码就会执行。**

这是设计如此——PHP 的 include 本来就是"把这个文件当代码跑"。

## 5.2 所以上传 + 包含 = Getshell

```
第一步：传 shell.jpg（内容是 GIF89a + php 代码）
        → getimagesize 通过，白名单通过
        
第二步：访问 index.php?page=../../uploads/shell.jpg
        → include 读进来，执行里面的 php
        
第三步：代码跑起来了
```

**上传漏洞给"能不能放进去"，包含漏洞给"能不能跑起来"。**

两个配合，才能从"传了个文件"变成"执行了代码"。

## 5.3 php://filter 是什么

`php://` 是 PHP 的内置"流包装器"（stream wrapper）。

它有几种模式：

| 包装器 | 作用 |
|---|---|
| `php://filter` | 在读取时做过滤/转换 |
| `php://input` | 读请求体（POST 的原始数据） |
| `php://stdin` / `php://stdout` | 标准输入输出 |
| `php://fd` | 文件描述符 |

**`php://filter` 的语法：**

```
php://filter/<过滤器>/resource=<目标文件>
```

如果同时用多个过滤器，用 `/` 分隔：

```
php://filter/read=convert.base64-encode/resource=index.php
```

拆开：

`php://filter/` —— 声明用过滤器

`read=convert.base64-encode` —— 读取时用 base64 编码（`read=` 可省略）

`resource=index.php` —— 目标文件

## 5.4 为什么它能读源码

**如果直接 include 一个 php 文件：**

```php
include("index.php");
```

**结果是它被执行了**，你再看到的是执行后的 HTML，看不到源码。

**用 filter 包一层：**

```php
include("php://filter/convert.base64-encode/resource=index.php");
```

**执行顺序变成：**

1. 先读 `index.php` 的原始字节
2. 用 base64 编码成字符串
3. 把编码后的字符串交给 include
4. include 解析这个字符串——**它现在全是 base64 字符，没有 `<?php` 标签，所以不执行任何东西**
5. 于是这段 base64 作为"输出"打出来

**你拿到 base64 串，解开就是源码。**

**这就是"绕过"的本质：把文件内容变换成不含代码标记的形式，让它无法被当作代码解析，只能作为文本输出。**

## 5.5 为什么用 `read=` 而不是 `write=`

`read=` 是"读取时处理"，`write=` 是"写入时处理"。

我们要的是"读源码但别执行"，所以用 `read`。

（`read=` 通常可以省略，PHP 会默认按 filter 链处理。）

# 第六部分：编码那三兄弟

## 6.1 URL 编码（百分号编码）

**用途：** 把 URL 里不能出现的字符转成 `%` + 十六进制。

| 字符 | 编码后 |
|---|---|
| 空格 | `%20` |
| `.` | `%2E` |
| `/` | `%2F` |
| `'` | `%27` |
| `<` | `%3C` |

**为什么需要：** URL 有自己的语法（`?` `&` `=` `/` 都是分隔符），如果参数值里含这些字符，会破坏结构。

**这条跟你的靶场直接相关：** 你看到的 `.php%00.jpg` 里的 `%00` 就是空字节，某些老版本 PHP 会在解码后截断字符串。

## 6.2 HTML 实体编码

**用途：** 把字符转成 `&...;` 形式，防止被当成 HTML 标签。

| 字符 | 实体 |
|---|---|
| `<` | `&lt;` |
| `>` | `&gt;` |
| `"` | `&quot;` |
| `'` | `&#x27;` 或 `&#39;` |
| `&` | `&amp;` |

**`&#x27;` 拆开看：** `&#` 表示"字符引用"，`x` 表示十六进制，`27` 是十六进制值 = 十进制 39 = ASCII 的 `'`。

**为什么相关：** XSS 攻击和防御都绕不开它。服务端输出用户内容时会转义，绕过转义就是绕过它。

## 6.3 Base64

**用途：** 把任意字节变成纯 ASCII 字符（A-Z a-z 0-9 + /），方便放进文本协议。

**编码规则：** 每 3 字节（24 bit）切成 4 段（每段 6 bit），每段映射到一个字符。

```
原文 3 字节 → 编码后 4 字符
```

**如果原文不是 3 的倍数，末尾用 `=` 补齐。**

**举例：**

`abc` 的 ASCII 是 `61 62 63`：

```
011000 010110 001001 100011
  24     22     9      35
  'Y'    'W'    'J'    'j'
```

结果：`YWJj`

**`base64url` 变体：** 把 `+` 换成 `-`，`/` 换成 `_`，去掉 `=`。JWT 用它，因为 `+` 和 `/` 在 URL 里有特殊含义。

## 6.4 三者对比

| 编码 | 触发位置 | 典型用途 | 能不能当代码执行 |
|---|---|---|---|
| URL 编码 | 浏览器发请求前 | 传参 | 解码后可能 |
| HTML 实体 | 服务端输出 HTML 时 | 防 XSS | 页面渲染后生效 |
| Base64 | 任意位置 | 传二进制、藏内容 | 不能（它就是文本） |

**关键区别：前两个是"传输层的转义"，Base64 是"数据格式的转换"。**

**Base64 编码过的代码，永远不会被执行**——因为它不含 `<?php` 这种标记。这就是 `php://filter` 能读源码的原因。

# 第七部分：串起来——你昨晚那个实验的完整解释

你昨晚做的是：传 `shell.php5`，改 Apache 配置，然后它执行了。

**用今天这套语言重讲：**

**第一步：** 你传上去的文件，字节内容是

```
3C 3F 70 68 70 20 65 63 68 6F 20 ...
  <  ?  p  h  p     e  c  h  o  ...
```

**第二步：** Apache 收到请求 `/hackable/uploads/shell.php5`。

**第三步：** 它检查 `FilesMatch \.php$`——`shell.php5` 结尾是 `5`，不匹配。

**第四步：** 不匹配就不设 handler，走静态文件那条路——**读整个文件，原样发给浏览器**。

**第五步：** 所以你在浏览器里看到的是 `3C 3F 70 68 70`... 解码成字符就是 `<?php echo ...`。

**第六步：** 你把 `FilesMatch` 改成 `\.php5?$`，重新加载。

**第七步：** 这次匹配了，handler 设置成功，文件交给 PHP。

**第八步：** PHP 读字节 → 词法分析 → 发现 `<?php` 起始标记 → 进入"代码模式" → 编译 → 执行 → 输出 `PWNED:working`。

**这八步，每一步都对应今天讲的一个概念。**

# 一句总结

**漏洞的本质，永远是两个东西对同一份数据的理解不一致。**

- 浏览器认为 `.php5` 是文本，Apache 认为它该交给 PHP
- `getimagesize` 认为它读完了，PHP 认为后面还有代码
- `include` 认为这只是个路径，PHP 认为内容里可能有代码

**找到"谁和谁的理解不一致"，就找到了漏洞。**
